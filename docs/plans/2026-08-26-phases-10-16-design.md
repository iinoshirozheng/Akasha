# AkashaDB Phases 10–16 Design

## Goal

Evolve the completed single-node MVP into a production-oriented single-node
engine and then a fault-tolerant distributed vector/document database without
moving storage or query correctness out of the Mojo kernel.

## Invariants

- Existing v1/v2 WAL, segment, and manifest data remains readable.
- Acknowledged writes survive process and machine crashes according to the
  documented fsync boundary.
- Point sequence order is the single source of truth across dense, sparse, and
  metadata state.
- Equal search scores remain ordered by ascending point ID.
- CPU scalar/SIMD execution remains the correctness oracle for quantized,
  parallel, GPU, and distributed execution.
- Python, HTTP, Arrow, and cluster transports remain adapters over Mojo-owned
  semantics.
- Every new durable format is versioned, checksummed, bounded, and covered by
  corruption, compatibility, and crash-ordering tests.

## Delivery sequence

### Phase 10: Incremental storage and compaction

Introduce a manifest generation that atomically references an ordered set of
immutable base and delta segments. Delta segments retain tombstones and only
contain point states newer than the previous checkpoint. Recovery applies
segments in sequence order, then replays newer WAL records. Leveled compaction
merges the newest state per point into a replacement base segment and drops
tombstones only when no older referenced segment can contain the point.
Checkpoint publication remains manifest-first: new files are fsynced, the new
manifest is atomically committed, WALs are rotated, and only then are files no
longer referenced by the committed manifest reclaimed. Automatic maintenance
uses a bounded engine-owned worker with a synchronous fallback and deterministic
shutdown.

### Phase 11: Snapshots, concurrency, and batch execution

Add immutable read snapshots pinned to manifest generations. Writers continue
through one ordered WAL pipeline while concurrent readers query stable snapshot
state. Batch mutation allocates one contiguous sequence range and commits
records atomically at the API boundary. Batch query shares validation, index
state, and worker-pool scheduling while preserving per-query deterministic
Top-K results. Segment reclamation waits until no snapshot pins the generation.

### Phase 12: Quantization, CPU parallelism, and persisted indexes

Add SQ8 first and product quantization second, each with versioned codebooks and
an exact rerank option. Parallel flat scan partitions ordinals into deterministic
ranges and merges bounded local Top-K heaps. Persisted HNSW and metadata index
artifacts are derived, checksummed caches: a mismatch causes safe rebuild, not
loss of authoritative data. Benchmarks gate recall, QPS, p95 latency, memory,
build time, and reopen time against the scalar oracle.

### Phase 13: GPU execution

Implement batched dot, squared-L2, cosine, and Top-K kernels in Mojo. A device
planner considers batch size, dimensions, candidate cardinality, transfer cost,
and available memory. CPU fallback is mandatory for unsupported hardware,
allocation failure, and small workloads. Differential tests compare GPU IDs,
scores, filtering, and ties with CPU execution within documented tolerances.

### Phase 14: Zero-copy interchange and projection

Add field projection to the Mojo query model and a trusted Arrow C Data bridge
with explicit producer/consumer ownership and release callbacks. Batch ingest
and result export accept fixed-size dense vectors, sparse lists, and typed
payload columns without pretending copied Python sequences are zero-copy.
Invalid schemas and premature release fail without mutating collection state.

### Phase 15: Operations and recovery tooling

Add online backup/restore, export/import, format inspection, checksum scanning,
orphan quarantine, metrics, tracing, resource limits, cancellation, and graceful
shutdown. Backups pin a manifest generation and include every referenced file.
Repair is conservative: it diagnoses corruption and only performs explicitly
safe recovery operations; it never silently invents acknowledged data.

### Phase 16: Distributed execution

Partition point IDs into versioned shards with a replicated write log per
shard. Consensus selects one leader and commits mutations before acknowledgement.
The coordinator fans out dense, sparse, hybrid, and metadata-filtered queries,
then performs deterministic global Top-K/RRF merge. Cluster metadata tracks
membership, shard epochs, replicas, and placement. Rebalancing transfers a
pinned snapshot plus log tail before ownership changes. Tests cover leader loss,
network partitions, stale epochs, duplicate delivery, replica catch-up,
rebalancing, and coordinator retry without violating consistency.

## Completion gates

Each phase requires focused red-green tests, the full Mojo/Python suite, crash
tests, release builds, smoke examples, format documentation, and a clean diff.
Performance phases additionally require committed benchmark harnesses and
correctness/recall thresholds. Phase 16 is complete only after deterministic
multi-process fault tests prove replication, failover, and distributed query
behavior; a single-process mock cluster is not sufficient evidence.
